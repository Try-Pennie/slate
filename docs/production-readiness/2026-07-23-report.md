# Production Readiness Report: Slate

Date: 2026-07-23. Advisory only (no ship/no-ship gate). Generated by the /production-ready audit: 19 domain auditors + adversarial verification of serious findings, all grounded in code with path:line evidence. Run: wf_acc9c791-708 (27 agents).

## Profile

Type: web-app. Hosting: Cloudflare Workers (OpenNext) at slate.trypennie.app + Supabase (Postgres/Auth), cron triggers and edge rate limits in wrangler.jsonc.
Stack: Next.js 16 App Router, TypeScript, React 19, Supabase (Postgres + Auth), googleapis, Tailwind v4, Luxon, Zod, pnpm; deployed via @opennextjs/cloudflare.
Auth: true. Database: true. PII: true. Public: true. Multi-tenant: false. Email: true. CI: true.

All 19 domains were applicable; none were skipped as N/A.

## Executive summary

Slate is in strong production shape at its core: booking correctness, concurrency, availability caching, alerting density, accessibility, and CI discipline are all unusually mature, with bespoke static guards that most teams never build. The gaps cluster at the edges of the system rather than in it: the site still answers over plain HTTP, dependencies are unwatched (Next.js sits several security patches behind, including a middleware-bypass advisory), nothing prevents a direct push to main, database restores have never been tested and PITR is not confirmed enabled, and consumer PII is collected on a public surface with no retention, erasure path, or compliance documentation. None of these are hard fixes; four of the six high-severity items are config or small-PR work. The advisory backlog below is deduplicated across all fourteen audit domains and ordered by severity, with each row ready to become a GitHub issue.

## What's solid

1. Concurrency and crash safety: unique-slot index, reservation-backed idempotent create, CAS reschedule leases, atomic reassign swap, and a leased outbox; among the strongest designs audited
2. Authorization: default-deny RLS on every table with a CI guard, server-side role gates on every action and route, impersonation with floor, ceiling, TTL, and audit trail, and no vertical escalation paths found
3. Rate limiting: layered edge plus DB limiting on every public path, per-key and per-IP budgets on the machine API, refund on server fault, and alert-on-block for leaked keys
4. Error handling: central chokepoints (log.ts, api/errors.ts, unwrap) enforced by bespoke static guards (capped reads, swallowed-error reads) that each carry a positive control
5. Testing discipline: 174 node suites plus 135 vitest files, regression tests tied to issue numbers, a pre-push gate running full CI parity, and a live production canary that books, reschedules, and cancels end to end
6. Deployment: atomic Worker deploys, migration-drift gating, one-command rollback, fail-loud missing-secret handling, and doc-drift guards that mechanically pin DEPLOY.md and README to reality
7. Accessibility: zero axe violations across 23 runs in both themes, full keyboard support, a permanent contrast guard in the test suite, and honored reduced-motion preferences
8. Observability foundations: structured logfmt logging through one chokepoint, a multi-lane dead-man's switch, throttled Slack alerting, and public health endpoints
9. Capacity: validated at the 200-agent design target with a real load/soak harness, published CPU headroom numbers, and documented platform ceilings

## Top risks

1. The production hostname serves over plain HTTP with no redirect, so a lead following an http:// link submits name, email, and phone in plaintext; a Cloudflare zone setting fixes it
2. No dependency vulnerability management: Dependabot is disabled, CI runs no audit, and Next.js 16.2.7 carries 4 high advisories patched in 16.2.11, including a middleware bypass that matters because Slate's session refresh runs in edge middleware
3. Database restores have never been tested and PITR is not confirmed enabled, yet PITR is the documented recovery path for the roll-forward-only migration policy; the implicit RPO is 24 hours of lost bookings nobody agreed to
4. Consumer PII (name, email, phone) is retained forever across bookings, booking_events, and webhook_deliveries with no retention window, no erasure path, and no compliance documentation for a lending-marketplace context
5. Nothing server-side prevents a direct push to main (branch protection unavailable on the free plan) and PRs self-merge in seconds, so the automated gates are the only reviewer
6. The entire safety net funnels through Slack alerting that has never been live-verified: an unconfigured or failing token silently disables all paging, which is the project's own documented false-confidence pattern

## Backlog (grouped by domain, severity-sorted within)

### secrets-transport

#### [HIGH] HTTPS/TLS enforced everywhere

Status: partial. Effort: S.

Evidence: Live probe: http://slate.trypennie.app/api/health returned 200 over plaintext with no redirect. HSTS applies only to /admin, /me, /login via the middleware matcher (src/middleware.ts:45-50, src/lib/security-headers.ts:23). The public booker collects lead name, email, and phone.

Remediation: Enable Always Use HTTPS (or an http-to-https redirect rule) for slate.trypennie.app on the Cloudflare zone; config-only, does not affect embeddability. Optionally serve HSTS on all responses since it does not restrict framing.

#### [MEDIUM] Webhook endpoint URL restricted to https

Status: partial. Effort: S.

Evidence: setWebhookEndpoint stores any non-empty URL (src/app/admin/actions.ts:814-815). An http:// endpoint would send every booking event (lead name, email, phone) plus the Regal API key Authorization header (src/lib/webhooks/wire.ts:52) over plaintext. Admin-only surface, but nothing stops the typo.

Remediation: Parse with new URL(...) and reject non-https schemes (allow http for localhost in dev). One-line check plus a test.

Remediation: Add scripts/test-licenses.ts in the existing node-script harness running pnpm licenses list --prod --json against an allowlist (libvips excepted). Defer SBOM until a concrete compliance requirement exists; note that stance.

### dr-backups

#### [HIGH] Backups taken AND restores tested (PITR)

Status: partial. Effort: M.

Evidence: Supabase daily backups are documented (DEPLOY.md:238-239) but PITR is documented as a not-yet-enabled add-on that only covers time after enablement (DEPLOY.md:241-244), with no record it was ever turned on. Zero evidence any restore has ever been performed; PITR is also the stated recovery path for the roll-forward-only migration policy (#607), so that recovery path may not currently exist. No backup-health monitoring either.

Remediation: (1) Confirm/enable PITR on the Supabase project now. (2) Run one restore drill into a scratch Supabase project, verify schema and row counts, time it, and record date plus duration in DEPLOY.md. (3) Add a monthly checklist item confirming recent successful backups. Optionally apply pending migrations to a Supabase branch before prod push for schema-heavy PRs.

#### [MEDIUM] DR runbook with RTO/RPO and post-restore reconciliation

Status: missing. Effort: M.

Evidence: No RTO or RPO stated anywhere (grep across README, DEPLOY.md, docs/ returns nothing); implicit RPO today is up to 24 hours of lost bookings. DEPLOY.md has rollback and backup sections but no DB restore step-by-step and nothing on reconciling a restored older database against Google Calendar events, live watch channels, and already-emitted Regal webhooks (booking mutations span Postgres plus Google, so a DB-only restore is guaranteed to diverge).

Remediation: Add a Recovery objectives paragraph (pick RPO/RTO; RPO of 1 hour forces the PITR decision) and a one-page Database restore runbook: Supabase restore steps, then reconciliation order (re-register watch channels, run sync/self-heal lanes to rebuild busy_blocks, sweep orphaned Google events, note Regal received webhooks for rolled-back bookings), then health verification.

### compliance-pii

#### [HIGH] PII retention, erasure, and regulatory posture

Status: missing. Effort: M.

Evidence: Consumer PII (attendee name/email/phone, 0001_init.sql:155-157) is collected on a public surface and retained forever: bookings are never hard-deleted, webhook_deliveries.payload keeps full attendee PII per delivery indefinitely, booking_events reason_detail persists forever. Only routing_decisions has retention (12 months). No DSR/erasure path, no compliance documentation anywhere (grep for gdpr/ccpa/privacy/erasure returns nothing), and CCPA/GLBA-adjacent obligations plausibly apply to a lending marketplace. Delivered outbox and webhook_deliveries rows are also a slow storage leak.

Remediation: Confirm CCPA/GLBA applicability with Pennie legal; define a retention window for completed/cancelled bookings and webhook_deliveries (null payload on success or prune older than N months, mirroring the prune-routing cron); add an erasure path (admin tool or documented SQL runbook) covering bookings, booking_events, and webhook_deliveries; record which tables are intentionally kept forever.

### input-injection

#### [MEDIUM] Security headers: CSP, nosniff, Referrer-Policy, HSTS on public surfaces

Status: partial. Effort: M.

Evidence: SECURITY_HEADERS (XFO DENY, frame-ancestors none, nosniff, Referrer-Policy, HSTS) applies only to /admin, /me, /login (src/lib/security-headers.ts:19-25; src/middleware.ts:38-51). No content CSP anywhere (documented as 'a separate effort', security-headers.ts:11-13). Public booker pages, manage-by-token pages, and all /api responses carry no nosniff, Referrer-Policy, or HSTS; next.config.ts sets no headers.

Remediation: Extend nosniff, Referrer-Policy, and HSTS to all responses (headers() in next.config.ts or a widened middleware, keeping frame-ancestors off embed paths), and schedule the nonce-based content CSP effort for the PII-bearing booker pages.

#### [MEDIUM] Size caps on public booking input

Status: partial. Effort: S.

Evidence: Both booking schemas accept unbounded strings and an unbounded prefill record: z.string().min(1) with no .max, prefill: z.record(z.string(), z.string()) (src/app/booking/route.ts:23-35; src/lib/booking/api-request.ts:38-57). A caller inside the rate limits can store multi-megabyte blobs that flow into Postgres, Google Calendar event bodies, and Regal/Cadence webhook payloads, where oversized payloads can fail downstream deliveries.

Remediation: Add .max() bounds on both schemas (name/email/phone <= 200 chars, prefill capped at ~20 keys x 500 chars or a serialized-size cap, bucketCode/timezone <= 64) and reject oversized bodies before insert.

#### [LOW] Admin booking search .or() filter injection

Status: partial. Effort: S.

Evidence: byText interpolates the raw query into a PostgREST .or() string with no escaping: attendee_email.ilike.${like} (src/lib/booking/search.ts:82-92). Commas/parens inject extra OR clauses or break the grammar; %/_ act as wildcards. Blast radius small: manager+ gated and org scoping is a separate ANDed .eq, so it only widens results within the caller's org, but legit queries containing commas fail.

Remediation: Escape with escapeLike and strip/encode PostgREST reserved characters before building the .or() string, or issue three separate .ilike() queries and merge, matching booking/service.ts:1502.

#### [LOW] CSRF defense-in-depth on cookie-authed admin mutation routes

Status: partial. Effort: S.

Evidence: POST /api/admin/bookings/[id]/cancel|reschedule|reassign and bulk-reassign rely solely on cookie auth with no Origin or Sec-Fetch-Site check (e.g. cancel/route.ts:18-32). Held together today by Supabase SSR cookies defaulting to SameSite=Lax, a third-party library default.

Remediation: Reject requests where Origin/Sec-Fetch-Site is present and not same-origin, in the admin mutation routes or middleware, removing single-point reliance on the library default.

#### [LOW] Google push channel token compared with plain !==

Status: partial. Effort: S.

Evidence: src/app/api/google/push/route.ts:15 uses token !== googleChannelToken(); #594 deliberately consolidated every other machine-endpoint secret onto timingSafeEqual (src/lib/bearer-auth.ts:26-46), leaving this as the one remaining plain-equality secret comparison.

Remediation: Compare via the existing timingSafeEqual from src/lib/bearer-auth.ts.

### rate-limiting

#### [MEDIUM] Abuse / bot prevention on public booking

Status: partial. Effort: M.

Evidence: No CAPTCHA/Turnstile/honeypot anywhere. The only bot control on POST /booking is the per-IP rate limit (3/min, 10/hr) plus shape-only attendee validation; email is never verified. A distributed bot can create real bookings with fake contacts, consuming finite agent slots and firing Google Calendar events and Regal/Cadence webhooks.

Remediation: Add Cloudflare Turnstile (turnstile-spin skill available) or WAF bot-score rules on POST /booking, and consider a per-attendee-email/phone booking cap alongside the per-IP one.

#### [LOW] Token-authed manage endpoints unthrottled

Status: partial. Effort: S.

Evidence: POST /api/bookings/[token]/cancel and /reschedule apply no rate limit (routes go straight from body parse to DB work). Token guessing is infeasible (nanoid(24), ~143 bits) and reschedule locks bound hammering, but garbage-token requests cost unthrottled unauthenticated DB round-trips.

Remediation: Add a small per-IP edge limiter (e.g. 20/min) at the top of the two [token] routes, mirroring the /api/routing pattern.

### observability

#### [MEDIUM] Slack alerting reliability (live-verified, self-checking, retry on failed send)

Status: partial. Effort: S.

Evidence: Three findings, one gap: (1) SLACK_BOT_TOKEN plus SLACK_ALERTS_CHANNEL were configured with no live verify run (project memory, #1019), so alert delivery on a real canary failure has never been proven. (2) Every alert path silently no-ops when slackConfigured() is false (src/lib/notify/dispatch.ts:18) with no degraded-state signal in production. (3) A failed Slack send still stamps the full alert cooldown (dispatch.ts:30-34), silently consuming the alert for 15-60+ minutes. This is the project's own documented false-confidence pattern applied to its entire paging layer.

Remediation: Run a positive control (deliberate canary failure, confirm the Slack message lands, revert); surface slackConfigured()===false as a degraded state in the monitor lane or /api/health; on a not-ok Slack result stamp a short retry window (~2 min) instead of the full cooldown, keeping the never-throws contract.

Backlog note: Follows closed #1019 (secrets configured, live verify never run). The degraded-state signal and cooldown-on-failed-send parts are new.

#### [LOW] 7-day log retention with no export

Remediation: Accept and document the 7-day forensic window explicitly in the incident-response expectations, or add a Logpush job shipping error-level lines to R2 if longer retention ever matters for compliance.

#### [LOW] SLOs undefined and no latency monitoring on user-facing paths

### error-handling

#### [MEDIUM] emitWebhook swallows endpoint-read and insert errors (permanent webhook loss)

Status: partial. Effort: S.

Evidence: src/lib/webhooks/emit.ts:136-141 destructures endpoints without consulting error: a transient DB error yields null, the outbox step is marked done (src/lib/booking/outbox.ts:53-57), no pending row is written, and the booking event is permanently lost to Regal/Cadence with no log or alert. emit.ts:160-164 also treats ANY insert error as the 23505 dedupe case. The file sits outside the swallowed-error scanner's scope, which is how it escaped.

Remediation: Throw (or log.error plus rethrow on the outbox path) on a real endpoints-read error so the step fails and retries; distinguish 23505 by code and fail loud on other insert errors; widen scripts/test-swallowed-error-reads.ts scope to src/lib/webhooks/*.

#### [LOW] Calendars classified gone are retried every rotation forever

Status: partial. Effort: M.

Evidence: No circuit breaker exists: a calendar classified gone (delegation revoked, account removed) keeps being re-attempted every sync rotation until a human deactivates the agent; the failure streak only tunes alerting (sync.ts:240-253), not attempt eligibility. Blast radius is bounded by per-tick caps, so this is noise/efficiency, not stability.

Remediation: Deprioritize or cap sync attempts for calendars with last_failure_kind=gone past a streak threshold (e.g. hourly instead of every rotation) until a human acts.

#### [LOW] Fail-loud cleanup: bare catches, unwrapped public GET, floating invalidateSlots

Status: partial. Effort: S.

Evidence: Three related small gaps: (1) ~30 bare .catch(() => {}) sites leave zero forensic trace on real work (recomputeBucketSlotsForToday at service.ts:696,2142,2176; deleteExpiredReservations at 2235; stopChannel at sync.ts:696-774). (2) GET /api/availability has no try/catch, so an unexpected throw returns a framework 500 with no internal_error Slack alert (route.ts:16-88). (3) The confirm-path invalidateSlots is a bare floating promise (service.ts:695-698) that Cloudflare can drop, the exact #503 class already fixed elsewhere via afterResponse.

Remediation: Replace bare catches on real work with .catch((err) => log.warn(...)) keeping the never-rethrow contract; wrap the availability GET in try/catch returning internalErrorResponse(err, "availability"); route invalidateSlots through afterResponse("booking-recompute", ...).

Backlog note: Verified: the invalidateSlots fire-and-forget at service.ts:695-698 is a documented deliberate tradeoff (comment cites the freshness sweep as backstop), not a missed #503 site. That sub-part is downgraded to optional; the bare-catch logging and the availability GET try/catch parts stand.

### compliance-audit

#### [MEDIUM] Tamper-evident audit logging

Status: missing. Effort: S.

Evidence: audit_log and booking_events are append-only by convention only: no REVOKE or trigger prevents UPDATE/DELETE, and all server code uses the RLS-bypassing secret-key client, so any compromised or buggy server path can silently rewrite audit history. No hash chaining or external log shipping; Worker logs retain 7 days.

Remediation: Add a migration creating BEFORE UPDATE/DELETE triggers that raise an exception on audit_log and booking_events (INSERT only), making the tables tamper-evident even against the secret key short of dropping the trigger.

#### [MEDIUM] Privacy policy link and contact disclosure on public booker

Status: missing. Effort: S.

Evidence: The standalone booker at slate.trypennie.app/book collects name, email, and phone with zero privacy policy, ToS, or consent copy (grep across booker surfaces returns no user-facing hits). ### concurrency-caching

#### [LOW] Outbox lease release not gated on the holder's own lease
